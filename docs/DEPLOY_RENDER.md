# Deploying Kairos AI to Render

Kairos ships as a **single all-in-one container**. One public Node/Express server
serves the built SPA, the REST API (`/api/v1`), and the playground WebSocket
(`/ws`), and proxies `/ml/*` to a co-located Python (FastAPI) ML service running
inside the same container. Everything is one Render web service — one URL, no
CORS, lowest cost.

```
                       ┌──────────────────────── Render web service ───────────────────────┐
  Browser  ──https──►  │  Node/Express (public :10000)                                      │
                       │    • GET /            → built SPA (frontend/dist)                   │
                       │    • /api/v1/*         → REST API            ── MongoDB Atlas       │
                       │    • /ws/playground    → WebSocket (Piston)                         │
                       │    • /ml/*  ──proxy──► uvicorn (127.0.0.1:8000)  ── Groq API        │
                       └────────────────────────────────────────────────────────────────────┘
```

## What's in the repo

| File                 | Purpose                                                            |
| -------------------- | ----------------------------------------------------------------- |
| `Dockerfile`         | Multi-stage build: Vite SPA → Node + Python runtime image         |
| `deploy/start.sh`    | Process supervisor: runs uvicorn (internal) + the Node API (public) |
| `render.yaml`        | Blueprint: one Docker web service + all env vars                  |
| `.dockerignore`      | Keeps the build context lean                                      |

## One-time deploy (Blueprint)

1. Push this repo to GitHub (already done if you're reading this).
2. In the **Render dashboard** → **New** → **Blueprint** → connect this repo.
   Render reads `render.yaml` and creates the `kairos-ai` web service.
3. Fill in the **secret** env vars (everything marked `sync: false`). Render
   prompts for these during blueprint creation:

   | Variable                     | Where to get it                                  |
   | ---------------------------- | ------------------------------------------------ |
   | `VITE_CLERK_PUBLISHABLE_KEY` | Clerk dashboard → API keys (`pk_live_…`) — public |
   | `CLERK_PUBLISHABLE_KEY`      | Same value as above                              |
   | `CLERK_SECRET_KEY`           | Clerk dashboard → API keys (`sk_live_…`) — secret |
   | `CLERK_JWT_KEY`              | Clerk → JWT templates (optional; leave blank if unused) |
   | `MONGODB_URI`                | MongoDB Atlas connection string                  |
   | `GROQ_API_KEY`               | Groq console (`gsk_…`)                            |

   `GUEST_TOKEN_SECRET` is auto-generated by Render (`generateValue: true`).

   > 💡 **Tip:** `render-upload.env` (repo root, gitignored) lists every variable
   > with the non-secrets pre-filled and the four secrets as placeholders. Copy the
   > secret values from there into the Blueprint prompts, or paste the whole file via
   > a service's **Environment → Add from .env**.

   > 🔴 **MongoDB Atlas — required before the first deploy.** In Atlas → **Network
   > Access**, add `0.0.0.0/0` (allow from anywhere). Render's free/starter tiers have
   > **no static egress IP**, so an IP allowlist blocks the connection. The API calls
   > `connectDatabase()` *before* it starts listening, so an unreachable Mongo makes
   > the container crash-loop and the health check never passes.
4. Click **Apply**. The first build takes a few minutes (it installs Node + Python
   deps and builds the SPA). Watch the logs.
5. When it's live, open `https://kairos-ai.onrender.com`.

### If you rename the service

The URL is `https://<service-name>.onrender.com`. If you change `name:` in
`render.yaml` (or Render appends a suffix because `kairos-ai` is taken), update
these three env vars to the real URL: `API_BASE_URL`, `WEB_BASE_URL`,
`ALLOWED_ORIGINS`. The frontend itself is same-origin and needs no URL changes.

## Environment variables

Non-secret values are committed in `render.yaml`. Secrets are set in the
dashboard. `GROQ_API_KEY` and the LLM/model vars are shared by both the Node API
and the Python ML service (both read the same names).

> **Rotate before going live.** If any real secret was ever committed to git
> history (Groq key, Clerk secret, Mongo password, guest secret), rotate it at the
> provider and set the new value in Render. Never put a secret in `render.yaml`.

## Health & logs

- Health check: `GET /api/v1/health` (Render uses this to gate traffic).
- ML health (through the proxy): `GET /ml/health`.
- Logs: Render dashboard → the service → **Logs**. You'll see both the uvicorn
  and the Node startup banners since they share one container.

## Local sanity check

You can't fully reproduce Render locally, but you can build the image:

```bash
docker build -t kairos-ai .
docker run --rm -p 10000:10000 --env-file .env.local kairos-ai
# then open http://localhost:10000
```

(`.env.local` must contain the runtime vars; see `.env.example`.)

## Notes / trade-offs

- **Free plan** spins down after inactivity and has 512 MB RAM. Two runtimes in
  one container is fine for light use; bump `plan:` to `starter` in `render.yaml`
  if you hit memory limits.
- **Interactive playground languages.** The slim image runs only Python, JavaScript,
  and TypeScript (via the bundled `tsx`), so the playground offers exactly those.
  To add compiled languages (C/C++/Java/Go/Rust/…), install their toolchains in the
  Dockerfile runtime stage and re-add their entries in `playground-exec.ts` +
  `playground.tsx` — expect a much larger image that needs a paid plan. (The
  problem-solver "Run" still supports many languages via the external Piston sandbox.)
- The API runs TypeScript directly via `tsx` (same as dev) — no brittle compile
  step. To switch to a compiled artifact later, give `@kairos/types` a JS build
  and point its `main` at the output.
- Want to split ML onto its own service later? Move the `/ml` block out, drop the
  Express proxy (gated by `config.isProduction` in `backend/api/src/app.ts`), and
  point `VITE_ML_BASE_URL` at the new service.
